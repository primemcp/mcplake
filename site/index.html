Open-source MCP gateway · Apache-2.0

Your identity provider decides what every AI agent can call — and what it gets to see.

mcplake is an identity-aware gateway for the Model Context Protocol. It authenticates every agent with your OIDC provider, grants MCP servers and individual tools from the token's claims, and strips the response fields a caller isn't allowed to see — before they reach the model's context window.

      Why it exists
      
MCP servers were built for one user. Your organisation has thousands.

      
An MCP server usually runs with one set of credentials and hands every tool, and every field, to whoever connects. That is fine on a laptop. It is not fine when agents act for hundreds of people with different jobs, clearances and data rights.

    

    

      
01 · over-privilege
Every agent gets every tool
A support bot that only needs lookups can also call drop_table. Prompt injection turns that from a risk into an incident.

      
02 · data leakage
Whatever the tool returns, the model reads
Salaries, SSNs, API keys and home addresses land in the context window, in logs and in the provider's hands — whether the user was entitled to them or not.

      
03 · a second identity system
Yet another place to manage users
Most gateways want their own users, API keys or "virtual keys" — and put SSO behind an enterprise licence. Your IdP already knows who everyone is.

    

  







  

    

      How it works
      
One pipeline, one rule engine, applied twice.

      
Every call — MCP tools/call or plain POST /v1/call — runs the same five steps. The claim rules that decide whether you may call a tool are evaluated again to decide what you get back.

    

    
    
      
  1. Authenticate
    Verify the JWT's signature against your IdP's JWKS, plus expiry, issuer and audience.
    ✗ 401 unauthorized
    2. 
      
  2. Authorize
    Access policies match claims with JSONPath + regex and grant exact (mcp, tool) pairs.
    ✗ 403 — before revealing whether the tool exists
    3. 
      
  3. Route
    The MCP must be registered, enabled and connected, and must advertise the tool.
    ✗ 403 mcp_disabled · 404
    4. 
      
  4. Call
    Forward over stdio (a supervised subprocess), Streamable HTTP or SSE.
    5. 
      
  5. Filter
    Filter policies matching the caller drop fields from every copy of the payload.
    ✗ fails closed if it can't enforce
    6. 
    

  







  

    

      What makes it different
      
Governance that goes all the way down to the field — for free.

      
Plenty of gateways decide which tools an agent may call. mcplake also decides what an allowed tool's answer contains, per caller, using the identity you already have.

    

    

      

        
Identity-aware field-level filtering

        
Not pattern-matching for things that look like PII — deterministic JSONPath removal of the fields this caller may not see. One get_employee tool serves HR (with salaries) and everyone else (without), with no duplicate servers and no trust in the agent to "ignore" data.

      

      

        
No leak through the copy you forgot

        
MCP results often carry the same data twice: structuredContent and JSON text in content blocks. mcplake applies every path to every copy — and if a filter applies but the payload is unparseable, it refuses to return it rather than pass it through.

      

      

        
Your IdP is the only source of truth

        
No gateway user database, no virtual keys to rotate. Move someone between groups in Keycloak, Okta or Entra ID and their tools — and their fields — change on the next call. OIDC isn't an enterprise add-on; it's the whole model.

      

      

        
Explainable decisions

        
The admin UI's request-path view takes a token's claims and shows, stage by stage, which policy granted or denied a call and which fields each filter removes — the same pipeline, the same status codes, before you ship a policy change.

      

      

        
A gateway agents can operate

        
Every admin operation — register an MCP, create a policy, flip a kill switch — is available as REST, in the web UI, and as MCP tools on an optional control server, gated by the same claim rules.

      

      

        
Built for networks with no way out

        
One Go binary, embedded SQLite, no telemetry, no phone-home. The only outbound traffic is to your IdP's JWKS endpoint and the MCP servers you register. PostgreSQL when you need it.

      

    

  







  

    

      Features
      
Everything included. Nothing behind a licence key.

    

    

      
OIDC / JWT authentication
Signature, expiry, issuer and audience checked on every call; JWKS cached.

      
Claims-based access policies
JSONPath + RE2 rules on any claim — roles, groups, tenant, region. Grant whole servers or single tools.

      
Field-level response filtering
Drop fields per caller, across every payload copy, fail-closed. Dead paths are logged.

      
Per-caller tool catalogue
One MCP endpoint aggregating every server as <mcp>__<tool>, filtered to exactly what the token grants.

      
MCP in, MCP out
Serve Streamable HTTP and SSE; reach servers over stdio, HTTP or SSE. REST POST /v1/call too.

      
Self-healing connections
Health-check loop reconnects servers that restart or start late; periodic schema refresh.

      
Admin web UI
React UI with OIDC PKCE login: servers, tools, policies, users — plus the request-path explainer.

      
Live changes, instant kill switches
Change policies at runtime; disable any server or policy reversibly, effective on the next call.

      
SQLite or PostgreSQL
Embedded by default; Postgres for shared state. Config-as-code in a single TOML file.

    

  







  

    

      Policy as configuration
      
The engineer's view above is twenty lines of TOML.

      
A rule is a JSONPath into the token and a regular expression. Policies are additive, filters are unioned, and anything not granted is denied.

      
    
        
  • Validated at load time — a broken rule stops the gateway, naming the entry.
    • 
        
  • Manage the same policies later through REST, the web UI or MCP tools.
    • 
        
  • No per-user state: the token carries everything.
    • 
      

    

    

      
config.toml


# Engineers may use the employee directory…
[[access_policies]]
name = "staff"
[[access_policies.match]]
path    = "$.role"
pattern = "^(staff|hr)$"
[[access_policies.grants]]
mcp   = "employee-directory"
tools = ["*"]

# …but never see pay or SSNs.
[[filter_policies]]
name        = "staff-hide-pay"
mcp         = "employee-directory"
tool        = "get_employee"
drop_fields = ["$.salary_usd", "$.ssn_last4"]
[[filter_policies.match]]
path    = "$.role"
pattern = "^staff$"

      Quickstart
      
See it deny, allow and redact in five minutes.

      
One command starts Keycloak, PostgreSQL, the gateway, the admin UI, MCP Inspector and several MCP servers — with demo users whose tokens get different tools and different fields.

      
    
        
  • Docker (Compose) or Podman, plus curl and jq.
    • 
        
  • Admin UI at localhost:8082 — sign in as mcplake-admin.
    • 
        
  • Point Claude Code, Cursor or any MCP client at localhost:9090/v1/mcp.
    • 
      

      
Full quickstart guide →

    

    

      

        
        
        
      

      

        
bash


git clone https://github.com/atsokha/mcplake.git
cd mcplake
docker compose up -d --build   # or: podman compose up -d --build

curl -s http://localhost:9090/healthz   # → ok

      

      

        
bash


TOKEN=$(curl -s -X POST \
  http://localhost:8080/realms/mcplake/protocol/openid-connect/token \
  -d grant_type=password -d client_id=mcplake-demo \
  -d username=alice -d password=alice -d scope=openid \
  | jq -r .access_token)

curl -s -X POST http://localhost:9090/v1/call \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"mcp":"employee-directory","tool":"get_employee",
       "arguments":{"employee_id":2}}' | jq .structuredContent
# salary_usd and ssn_last4 are gone. Try username=bob → 403.

      

      

        
bash


# Claude Code
claude mcp add --transport http mcplake http://localhost:9090/v1/mcp \
  --header "Authorization: Bearer $TOKEN"

# Any client with a JSON config (Cursor, VS Code, …)
{ "mcpServers": { "mcplake": {
    "url": "http://localhost:9090/v1/mcp",
    "headers": { "Authorization": "Bearer <token>" } } } }

FAQ
Questions people ask.

    

      
What is an MCP gateway?
A reverse proxy between AI agents (MCP clients) and the MCP servers that give them tools. Instead of every agent connecting to every server, they connect to the gateway, which authenticates the caller, decides what it may use, forwards the call and returns the result. mcplake is an MCP gateway focused on identity: your OIDC provider's token claims decide both access and what data comes back.

      
How is mcplake different from Bifrost, MCPX or agentgateway?
mcplake is a dedicated MCP gateway, not an LLM gateway. Its distinguishing feature is identity-aware, field-level response filtering: the same claim rules that grant a tool also decide which fields of that tool's answer the caller receives — applied to every copy of the payload, failing closed. And everything, including OIDC-based access control, is Apache-2.0 with no enterprise tier. If you need LLM routing, run mcplake alongside an LLM gateway.

      
Does it work with Claude Code, Cursor and other MCP clients?
Yes. mcplake is itself an MCP server: point any client that can send an Authorization header at /v1/mcp (Streamable HTTP) or /v1/sse. The client sees one catalogue, named <mcp>__<tool> and filtered to its token.

      
Which identity providers are supported?
Any OIDC provider that publishes a JWKS endpoint — Keycloak, Okta, Microsoft Entra ID, Auth0, Google, Dex, Authentik and so on. Rules can match any claim, including nested ones such as Keycloak's realm_access.roles.

      
Is it the same as PII detection?
No, and that is deliberate. Detection guesses what looks sensitive; mcplake removes exactly the fields you name, for exactly the callers you name. It is deterministic, testable and explainable. You can still run a detector behind it.

      
Can it run in an air-gapped network?
Yes. One Go binary, embedded SQLite by default, no telemetry, and no outbound calls except to your IdP's JWKS endpoint and the MCP servers you register.

      
Is it really free? What's the catch?
No catch. Apache-2.0, no paid tier, no enterprise edition, no feature gating, no telemetry. The goal is a gateway the MCP community can trust and build on.
